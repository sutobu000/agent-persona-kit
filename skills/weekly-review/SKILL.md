# 週次点検

**目的は「相手がスマホで現況を一目で確認できる状態」を保つこと。** 放っておくと記録は必ず腐る。

実行日: {{REVIEW_DAY}}

記憶の正本: `{{MEMORY_TOOL}}`

`README.md`の`scope`が今回の作業範囲と一致するときだけ、この正本を点検する。

## 1. プロジェクトノートの整理

最初に`projects/index.md`を読み、索引と実ファイルの対応を確認する。

各ノートについて確認する。

- 冒頭に **「現況(日付)」「タイムライン」「次の一手(誰が)」** が揃っているか。無ければ作る。
- 経緯の詳細が冒頭を押し下げていないか。**原文は消さず、下へ移す。**
- 専門用語・略語・内部コード名に、初出のひとこと説明が付いているか。
- 動いていないノートに `status: paused / done / archived` と**再開条件**が書かれているか。書いて一覧の下へ移す。
- 「次の一手」が古くなっていないか。担当が誰か書いてあるか。

## 2. 申し送りの退避

- `handover.md`を確認し、最大{{HANDOVER_CAP}}件を維持する。
- 申し送りは直近{{HANDOVER_CAP}}件で流れる。**プロジェクトの話が溜まっていたらノートへ移す。**
- 申し送りに残すのは、面をまたいで今すぐ知るべき横断的な1〜2文だけ。
- 流れて消えた記録が必要なら、記憶データのバージョン履歴から復元してノートへ入れる。

## 3. 自作資産の棚卸し

**作りっぱなしを防ぐのがこの節の役目。**

- この1週間で**一度も使われなかった**skill・サブエージェントを挙げる。
- それぞれに「なぜ使われなかったか」を1行付ける(用途が消えた / `description` が呼ばれない書き方 / 既存と重複)。
- **削除を提案する。削除するかは相手が決める。**勝手に消さない。
- `description` が悪いだけなら、削除ではなく書き直しを提案する。

## 4. 設定・事実のドリフト

- 環境間で設定がずれていないか。揃える作業は着手してよい。
- 指示ファイルに書いた外部サービスの事実(料金・仕様・モデル)が古くなっていないか。
- 使わなくなったツール・MCPサーバーの登録が残っていないか。

## 5. 昇格の判断

- 一時メモに埋もれている知見のうち、**恒久ルールに上げるべきものを挙げる。**
- 同じ手順を2回以上繰り返していたものは、skill化の候補として挙げる。

## 出力

点検の結果は「事後報告の型」で出す。**削除・変更の提案は、相手が選べる形(選択肢+推奨)で並べる。**
