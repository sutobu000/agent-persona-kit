# 定期情報収集

**目的は「相手の前提が古いまま進むのを防ぐこと」。** 全件を読ませることではない。

## 実行のしかた

- **定期実行の仕組みがある環境**: 毎朝1回、前日の更新を追記する自動ジョブとして回す。
- **無い環境**: セッション冒頭の状況確認に組み込み、**手動の手順書として同じ順序で辿る。**この場合「自動収集ではない」と明記する。

## 1. 情報源

固定した一次情報源から始める。検索から始めない。

- 一次情報源: {{PRIMARY_SOURCES}}
- 使っているツール・サービスの公式変更履歴(リリースノート・changelog)。
- 進行中プロジェクトが依存しているライブラリの更新。

## 2. 絞り込み

拾った更新を、次の3つのどれかに当たるものだけに絞る。**当たらないものは捨てる。**

1. 進行中の作業のやり方が変わる。
2. 相手が持っている前提が古くなる。
3. 保留していた判断の前提が変わり、再開できる。

## 3. 記録

- 追記先は記録の器(ノート)。**申し送りには書かない**(横断的な1〜2文だけの器なので)。
- 1エントリ=1件。絶対日付({{DATE_EXAMPLE}})を付ける。
- 出典URLを必ず付ける。**確認できなかったものは「未確認」と明記する。**
- 特に重要なものには「要注意」の印を付ける。

## 4. 伝え方

- **1〜3行だけ**伝える。全件を並べない。
- 「要注意」印のものは、短くても必ず触れる。
- 相手の前提と食い違う情報が出たら、遠慮せず根拠付きで指摘する。黙って合わせない。

## 5. 週次のまとめ

{{REVIEW_DAY}}に、その週の分をまとめる。

- 各プロジェクトノートの「次の一手」に反映すべきものを挙げる。
- 反映は提案で止めず、影響が小さいものはその場で書き換えるところまでやる。
